# 受け入れ項目の作り方

エビデンスで何を確かめるかを決める決まり。撮る前にこの手順で項目を作り、見直して漏れを無くしてから撮る。

元は dev-workbench の `skills/evidence-pack/reference/cases.md`(汎用版)。この拡張機能向けに、正本の置き場所・影響を受けやすい共通処理・見直しの頼み方を直している。
受け入れ項目の一覧を利用者に確認してもらう必要はない(その代わり、撮る前の見直しは自分と別の目の両方を省かない)。

仕様を決める時や、テストを書く時も、同じ見方を使う。「どう確かめるか」が言えない仕様は、まだあいまいなところが残っている。

## ゴール

項目は、次の5つを満たすように作る。足すか迷った項目は、どれに効くかで決め、どれにも効かないものは足さない。

| # | ゴール | 満たし方 |
|---|---|---|
| 1 | Issueや仕様に書かれた要件を満たしていることを確かめられる | 要件を1つずつ書き出し、1つの要件に1つ以上の項目を置く(「要件」) |
| 2 | 書かれていないが、変更で動きが変わりうるところを確かめられる | 差分の分岐・共通の処理を使う別の機能・変わらないはずの動きを拾う(「既存機能への影響」「設計で追加した仕様」) |
| 3 | 自動のテストで確かめられていない動きを確かめられる | 画面の流れ・実際のデータ・外のサービスとのやりとり・画面にだけ出る文言など、テストで見ていないものは必ず項目にする |
| 4 | 初めて見た人が、聞き返さずに判定できる | 期待する結果を具体的な値で書く。「正しく」「適切に」のような判定できない言葉を残さない |
| 5 | むだが無い | 同じ操作・同じ結果を確かめる項目を重ねない。どのゴールにも効かない項目を足さない |

## 正本は受け入れ項目の一覧

このプロジェクトでは、エビデンスを撮ってから PR を作る(issue-handler のステップ10 → 11)。
そのため、受け入れ項目は先に `00-cases.md` の「受け入れ項目」に、節(`###`)と番号つきの一覧で書き、これを正本にする。

- エビデンスの `manifest.json` の節と項目は、この一覧を**順番も文言もそのまま**写す
- PR 本文の Test plan も、この一覧を**順番も文言もそのまま**写し、エビデンスで○だった項目にだけチェックを付ける(手順は SKILL.md)
- 一覧に無い操作は撮らない。撮っている途中で足りないと気づいたら、先に一覧に足してから撮る
- PR がすでにあり、Test plan に項目が書かれている時は、それを正本にして同じ見直しをかけ、足りない項目を Test plan に足す

## 3つの見方

項目は、どれも次のどれか1つに入る。受入確認の見出しと `sections` もこの3つに分ける(項目が無い節は作らない)。

| 節 | 何を確かめるか | どこから拾うか |
|---|---|---|
| 要件 | Issueや仕様に書かれた要件を満たしていること | Issueの本文、決めた仕様 |
| 既存機能への影響 | 変更が、もとからある機能を壊していないこと。特に共通の処理を変えた時 | 差分と、変えた処理(関数・型・設定・スタイル・保存のキーなど)を使っている場所 |
| 設計で追加した仕様 | 要件には無いが、設計や実装の途中で決めた動き | 相談して決めたこと、実装中に決めた細かいこと、レビューで足した直し |

「要件」に置くのは、Issueや仕様に**書かれたこと**だけ。書かれていない動きは、ほかの2つに置く(要件を勝手に増やさない)。

### 要件

1. Issueと仕様を、**1行に1つの要件**になるまで分ける。「AとBができる」は2つにする
2. 要件に番号(R1, R2, …)を振る
3. 要件ごとに1つ以上の項目を作る。**できないこと・失敗した時の振る舞いを先に**考える(後回しにすると漏れる)
4. 不具合を直すIssueは、**直す前に起きていたことが起きない**ことを必ず項目にする

### 既存機能への影響

1. 差分から、変えた処理(関数・定数・型・設定・スタイル・保存のキーなど、プロジェクトにあるもの)を書き出す
2. それを**使っている場所を検索で探す**。変えていない機能から使われていれば、そこが影響を受ける
3. 影響を受ける場所ごとに、いつもの操作が今までどおり動く項目を作る。共通の処理を変えた時は、**使っているすべての機能**で1つずつ
4. 動きを狙って変えた時は、変わった後の動きは「要件」か「設計で追加した仕様」で確かめ、ここでは**変わってはいけないところ**だけを確かめる
5. 保存するデータの形を変えた時は、前に保存したデータで開けることを項目にする

この拡張機能で、変えると影響が広いもの:

| 変えたもの | 影響を受ける場所 |
|---|---|
| `popup.js`(タブ管理・UI 構築・共通ヘルパー) | すべてのタブ |
| `ui-helpers.js` / `utils.js` | それを使うすべてのモジュール(`_TkUI` / `_TkUtils` を grep する) |
| `styles/base.css` などの共通 CSS・component ファイル | それを読む画面すべて(ポップアップと、プレビューなどの独立ページ) |
| `modules/screenshot/annotation-*.js` | スクリーンショットのプレビューと動画のプレビューの両方 |
| ストレージキー(`TAB_MANIFEST` の `storageKey` など) | そのキーを読み書きする場所と、ストレージ画面 |
| `manifest.json`(権限・ホスト) | その権限を使うすべての機能 |

### 設計で追加した仕様

要件の文には出てこないので、意識して拾わないと漏れる。

- 相談して決めたこと(数値・置き場所・名前・操作のやり方・文言)
- 実装中に決めた細かいこと(押せない時の見せ方、最小の大きさ、範囲外の値の扱い、エラーの出し方など)
- レビューで足した直し
- 空・上限を超えた入力・対象が無い時などに、どう振る舞うと決めたか

## 観点の出どころ

3つの見方で拾ったあと、次の表を**上から順に総なめ**にして、差分に当てはまるのに項目が無いものを足す。当てはまらない行は飛ばしてよい。

| 出どころ | 拾い方 |
|---|---|
| 分岐 | 差分の条件分岐・途中で抜けるところ・例外。繰り返しは 0件・1件・複数件。1つの分岐に1つ以上 |
| 入力 | 入力ごとに、必須か・型・桁数・文字の種類・初めの値。境界(最小−1・最小・最大・最大+1)。空の入力の変わり種(空、空白だけ、前後に空白) |
| データの状態 | 実際にありうる形(未登録・複数・削除済み・古い形のまま保存されたもの) |
| 権限 | 使う人の役割や権限の組み合わせ |
| 状態の移り変わり | 新規・編集・削除・保存の前後など。移れない組み合わせも書く |
| 新しく作る時と、既存を開く時 | 同じ部品でも、作る道筋と読み込む道筋が分かれていることがある。両方を通す |
| 外とのやりとり | ほかの機能・ほかのサービス・時間が経つと変わるものとの整合。失敗した時の振る舞い |
| 画面や文言の変更 | 見た目や文言が変わったら、変わった画面ごとに崩れていないか。ポップアップの決まった幅や、プレビュー右側の狭い操作パネルなど、表示が窮屈になる場所ではとくに(文字の重なり・はみ出し・ツールチップの隠れ) |
| 条件で振る舞いが分かれる変更 | 条件で変わる側だけでなく、**変わらない側(今までどおり)の確認も対にして**置く。変わる側の確認を1つずつ並べ、それぞれに今までどおりの確認があるかを突き合わせる |
| 画面の外の入り口・出口 | ファイルの読み込み・書き出し・通知・ログなど、画面とは別の道を通るもの |

拾い終えたら、**差分を1行ずつ見直し、どの項目にも結びつかない行が残っていないか**を確かめる。残っていれば、観点が漏れている。

### 漏れを防ぐ技法

当てはまる時だけ使う。

| 技法 | 使う時 | やること |
|---|---|---|
| 同値分割・境界値 | 値に範囲・上限・件数がある | 有効・無効のまとまりと、その境目(最小−1・最小・最大・最大+1、0件・1件・上限の件数)を出す |
| 組み合わせの表 | 条件が複数あり、組み合わせで結果が変わる | 条件×条件の表を作り、**全部の組み合わせを先に出してから**間引く。先に間引くと漏れる |
| 状態の移り変わり | 画面やデータが状態を持つ | 状態×操作を並べ、移れない組み合わせも書く |
| エラー推測 | 似た不具合やミスに心当たりがある | 前に起きた不具合・起きやすい間違いを並べる |

## 項目の書き方

- **前提 → 操作 → 期待する結果** の順で書く。前提は短く(2行まで)
- **1つの項目で確かめるのは、1つの操作の結果だけ。** 1つの操作で複数のことが見えるなら、1つの項目に結果を並べてよい。操作と結果の組が2つ以上になるなら分ける
- **期待する結果は具体的な値で書く。** 画面に出る文言・数値・状態をそのまま書く。「正しく表示される」「名前を含むファイル名」ではなく「`アイデア帳_2026-11-03.csv`」のように書く。直す前の動きと違う時は、直す前の動きも添える
- **見る人の言葉で書く。** 画面に出ている言葉を使い、コードの名前(関数名・変数名・内部のID)を書かない
- 結果を確かめる時は**値を読む**。画面の要素の状態・出力・戻り値・保存された値・ログなどを読んで `checks` に書く。画像や動画は、それを見せるためのもの
- 仕様から期待する結果が決まらない項目は、推測で埋めない。撮る前に伝えて、決めてもらう
- 確かめられなかった項目も消さずに `partial` にし、`note` にわけを書く

### 確かめ方と残すもの

| 確かめ方 | 残すもの |
|---|---|
| 画面で、1つの状態を見れば済む | 画像(既定) |
| 画面で、前後の変化や流れを見せないと判らない | 動画 |
| コマンドで確かめる(lint・テストなど) | 出力のテキスト(`attachments`) |
| 文書を読んで確かめる | 根拠にした箇所を書いたテキスト(`attachments`) |

迷ったら画像にする。1枚で伝わらないと分かってから動画にする。

### 自動のテストとの関係

- 自動のテストで確かめているからといって、項目から外さない。テストが本当にその操作をしているかは、テストのコードを読んで確かめる(ファイル名だけで決めない)
- テストの結果は、コマンドの出力として `attachments` に添える

### 対象外

確かめない理由がはっきりしているもの(差分が触れていない機能など)は、`notes` に「確かめていないこと」として理由つきで書く。
**差分が触れているものは、対象外にしない。**

### 変更前と比べる(動きを変えないことが目的の変更)

共通化・ファイルの分け直しなど、動きを変えないことが目的の時は、次を混ぜずに別の項目にする。

1. 変更前のコードで、見るべき画面や出力を撮る(判定はしない)
2. 変更後のコードで、期待する結果を満たすかを確かめる
3. 1と2を1つずつ見比べ、意図しない違いが無いことを確かめる。違いがあれば、狙った直しか、壊したものかを `note` に書く

## 重なりをまとめる

同じ操作・同じ結果を確かめる項目が、節をまたいで重なっていないかを見る。

- まとめる前に、消す側の期待する結果を**1つずつ**、残す側で確かめているか照らし合わせる。題名や操作が似ているだけで決めない
- 残す側に足りない確かめがあれば、残す側に足してからまとめる。足せないなら、まとめない
- 要件を確かめる項目は、同じ要件を確かめる別の項目が残る時だけまとめてよい
- 1つの要件・1つの影響先・1つの決めたことに結びつく項目が、まとめた結果ゼロにならないようにする

## 対応表

項目を作ったら、どこから拾ったかと項目の対応を `00-cases.md` に書き、フォルダに入れて `attachments` に載せる。
ビューアで「何をもとに、何を確かめたか」を追えるようにするため。

```markdown
# 受け入れ項目(#119 注釈の改善)

## 受け入れ項目
### 要件
1. 吹き出しに文字を入れると、文字の上下に余白が 10px ずつ空く
2. 吹き出しの幅を超える英文は、単語の切れ目で折り返す
### 既存機能への影響
3. 動画のプレビューでも、吹き出しの文字が折り返して描かれる
### 設計で追加した仕様
4. 「。」は行頭に来ない(セルフレビューで追加)

## 対応表
| 見方 | どこから | 項目 |
|---|---|---|
| 要件 | R1 吹き出しの上下の余白を広げる | 1 |
| 要件 | R2 長い文字を折り返す | 2 |
| 既存機能への影響 | annotation-shapes.js(スクショ・動画の両方で読む) | 3 |
| 設計で追加した仕様 | 句読点・括弧の禁則処理(セルフレビューで追加) | 4 |

## まとめた項目
- なし

## 確かめていないこと
- 動画への書き出し結果(録画データの用意が必要なため。項目 3 は partial)
```

## 撮る前の見直し

### 自分で見直す

項目を作り終えたら、ゴールに沿って次を1つずつ確かめる。満たしていなければ、項目を足すか直してから撮る。

- [ ] (ゴール1)すべての要件(R1, R2, …)に、その要件を満たしたかを判定できる項目がある
- [ ] (ゴール2)差分のどの行も、どれかの項目に結びついている。観点の出どころの表を総なめにした
- [ ] (ゴール2)変えた処理を使っている場所をすべて探し、影響を受ける場所ごとに項目がある
- [ ] (ゴール2)条件で振る舞いが分かれる変更に、変わらない側の確認が対になっている
- [ ] (ゴール2)相談して決めたこと、実装中に決めた細かいこと、レビューで足した直しのすべてに項目がある
- [ ] (ゴール3)自動のテストで見ていない動きに、項目がある
- [ ] (ゴール4)すべての項目で、期待する結果が具体的な値になっていて、`checks` に書く値が決まっている
- [ ] (ゴール4)判定できない言葉・コードの名前が残っていない
- [ ] (ゴール5)同じことを確かめる項目が重なっていない。まとめた項目は対応表に書いた
- [ ] 確かめられないものは「確かめていないこと」にわけを書いた

### 別の目で見直す

書いた本人の見直しだけでは、同じ思い込みで漏れる。**書き手とは別の文脈**に、受け入れ項目・差分・Issueだけを渡し(書いた途中の考えは渡さない)、漏れを探してもらう。
ここでは Agent ツールで `general-purpose` のサブエージェントを起動し、`00-cases.md`・`git diff <base>` の範囲・イシュー番号(本文と確定仕様コメントを `gh issue view <番号> --comments` で読ませる)・このファイルのパスを渡す。直さずに指摘だけを返すよう頼む。

- 見てもらうもの: 上の「自分で見直す」の各項目と、ゴールの5つ。ゴールごとに「満たしている/満たしていない」と根拠を返してもらう
- 返してもらう形: 重大度つきの一覧。直すのは書き手

| 重大度 | 意味 |
|---|---|
| P1 | 漏れ。項目を足さないといけない(どの項目でも通らない分岐、判定できない要件、影響先の抜け) |
| P2 | 中身の誤り。期待する結果・前提が違っていて、判定できない、または誤って○になる |
| P3 | 書き方の揺れなど |

- 項目を増やす指摘は、要件が判定できない・誤って○になる、といった重いものに限ってもらう(むやみに増やさない)
- 調べて問題が無かったところも一言ずつ返してもらう(調べていないところを「問題なし」としない)
- P1・P2 を直す。P1 があった時だけ、もう一度見てもらう(2回まで)。2回目でも P1 が残るなら、利用者に判断を仰ぐ
