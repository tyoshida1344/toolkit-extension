# ケース（確認項目）の作り方

エビデンスで何を確かめるかを決めるルール。撮影の前にこの手順でケースを作り、セルフレビューで漏れを潰してから撮る。
ケースの一覧を利用者に確認してもらう必要はない（その代わり、セルフレビューは省かない）。

`issue-handler` の仕様確定・実装でも同じ3つの観点を意識する。仕様を決める時点で「どう確かめるか」が言えない仕様は、曖昧さが残っている。

## 3つの観点

すべてのケースは、次のどれか1つの観点に属する。manifest.json の `sections` もこの3つに分ける（該当するケースが無い節は作らない）。

| 節（`sections[].title`） | 何を確かめるか | 出典 |
|---|---|---|
| 要件 | イシューに書かれた要件が満たされていること | イシュー本文、確定仕様コメントの「詳細仕様」 |
| 既存機能への影響 | 変更が既存の機能を壊していないこと。特に共通処理を変えた場合 | `git diff <base>` と、変更した関数・CSS・ストレージキーの利用元 |
| 設計で追加した仕様 | 要件には無いが、設計・実装の段階で決めた動作 | 確定仕様コメントの「確認した不明点と決定」「実装方針」、実装中に決めた細部、セルフレビューで足した修正 |

### 要件

1. イシュー本文と確定仕様の「詳細仕様」を、**1行に1つの要件**になるまで分ける。「A と B ができる」は2つの要件にする
2. 要件ごとに番号（R1, R2, …）を振る
3. 各要件に最低1ケース作る。加えて、要件の文言から読み取れる次のものはケースを分ける
   - 操作の手段が複数ある（ボタンとショートカット、クリックとキー操作）→ 手段ごと
   - 値に幅がある（上限・下限・空・長い入力・日本語と英語）→ 代表値と端の値
   - 既定値が決まっている → 初期状態を開いた直後の値
4. バグ修正のイシューは、**直す前に起きていた現象が起きないこと**を必ずケースにする（再現手順をそのまま使う）

### 既存機能への影響

1. `git diff <base> --name-only` で変更ファイルを出し、変更した関数・定数・CSS クラス・id・ストレージキーを書き出す
2. それぞれの**利用元を grep で探す**。利用元が変更していない画面・機能にあれば、それが影響範囲
3. 影響範囲ごとに、代表的な操作が今までどおり動くケースを作る
   - 共通処理（`popup.js` のヘルパー、`ui-helpers.js`、`utils.js`、複数画面で読む `modules/screenshot/annotation-*.js` など）を変えた場合は、**それを使うすべての画面**で1ケースずつ
   - 既存の挙動を意図して変えた場合は、変わった後の動作を「要件」か「設計で追加した仕様」で確かめ、ここでは**変わってはいけない部分**だけを確かめる
4. ストレージキーやデータの形を変えた場合は、変更前に保存されたデータで開けることをケースにする

### 設計で追加した仕様

要件を満たすために、設計や実装の途中で決めた動作。要件の文面には出てこないので、意識して拾わないと漏れる。

- 確定仕様コメントで「Q → A」として決めたこと（数値・配置・名称・操作方法）
- 実装中に決めた細部（無効状態の見せ方、最小サイズ、範囲外の値の補正、禁則処理、エラー時の表示など）
- セルフレビュー（review-perf / review-regression / review-ux）で足した修正
- 異常系・境界で選んだ振る舞い（空の入力、上限を超えた入力、対象が無い時の操作）

## ケースの書き方

- **1ケース = 1つの確かめ**。`title` は「〜すると〜になる」と期待結果まで書く（「〜を確認」で終わらせない）
- **判定は値で行う**。見た目だけで判定せず、DOM の状態（`hidden` / `disabled` / `value`）、canvas の画素、保存された値などを読んで `checks` に書く。画像・動画は判定を見せるための添え物
- 画像か動画か: 1つの状態を見れば済むものは画像、操作の前後や流れを見せる必要があるものは動画（手順3の表）
- `result`: すべての `checks` が期待どおりなら `ok`、確かめられなかった・一部だけのものは `partial`、期待と違えば `ng`。**撮れなかったケースも消さず** `partial` にし、`note` に理由を書く
- ケースの番号はファイル名と揃える（`id: "3"` → `03-…png`）

## トレーサビリティ表

ケースを作ったら、出典とケースの対応表を `00-cases.md` に書き、エビデンスのフォルダに入れて `attachments` に載せる。
ビューアで「何を根拠に、何を確かめたか」を追えるようにするため。

```markdown
# ケース一覧（#119 注釈の改善）

| 観点 | 出典 | ケース |
|---|---|---|
| 要件 | R1 吹き出しの上下の余白を広げる | 1 |
| 要件 | R2 長い文字を折り返す | 2, 3 |
| 既存機能への影響 | annotation-shapes.js（スクショ・動画の両方で読む） | 8, 9 |
| 設計で追加した仕様 | 句読点・括弧の禁則処理（セルフレビューで追加） | 12 |

## 確かめていないこと
- 動画の書き出し結果（録画データの用意が必要なため。ケース 9 は partial）
```

## セルフレビュー（撮る前に必ず行う）

ケースを作り終えたら、次を1つずつ確かめる。満たさない項目があればケースを足す・直す。結果は完了報告に1行で書く（例: 「ケースのセルフレビュー: 漏れ2件を追加」）。

- [ ] 要件（R1, R2, …）のすべてに、ケースが1つ以上ある
- [ ] 要件の操作手段・値の幅・既定値を、ケースに分けている
- [ ] 変更した関数・CSS・ストレージキーの利用元をすべて洗い出し、影響範囲ごとにケースがある
- [ ] 共通処理を変えた場合、それを使うすべての画面にケースがある
- [ ] 確定仕様の「Q → A」、実装中に決めた細部、セルフレビューで足した修正のすべてにケースがある
- [ ] 異常系・境界（空・上限超え・対象が無い時）を、少なくとも要件1つにつき検討した
- [ ] すべてのケースで、判定に使う値（`checks` に書くもの）が決まっている
- [ ] 1つのケースで2つ以上を確かめていない／同じことを確かめる重複ケースが無い
- [ ] 確かめられないものは「確かめていないこと」に理由付きで書いた
