# Review Perf — パフォーマンスレビュー

変更差分を「コード量を減らせないか」「処理を軽くできないか」の2軸で確認する。

## 対象の特定

1. 変更ファイルを取得する:

```sh
git diff main --name-only
```

2. 変更ファイルの全体を読む（diff だけでなく前後の文脈が必要）
3. 変更ファイルを参照・利用している関連ファイルも特定して読む（`Toolkit.*` API の利用元、同じ CSS クラスを使うファイルなど）

## 確認観点

以下の観点で変更箇所とその周辺を確認する。全てを機械的にチェックするのではなく、**実際に効果がある指摘** に絞る。

### コード量の削減

- 既存の `Toolkit.*` ヘルパー（`copyButton`, `bindState`, `modal`, `getTabsById`, `tryRegex`, `iconButton`, `showToast` 等）で置き換えられる独自実装がないか
- 重複するロジックを関数に抽出できないか
- 不要な変数・関数・条件分岐がないか
- 同じ DOM 要素への複数回アクセスを変数にキャッシュできないか
- テンプレートリテラルで簡潔にできる文字列結合がないか

### 共通処理の再利用・切り出し

既存の共通処理を使わず再実装していないか、逆に今回追加したコードの中に新たに共通化すべき重複がないかを、両方向で確認する。

- CSS: `styles/base.css` の `var(--tm-*)` デザイントークンを使わず生の hex を書いていないか。`.tm-btn` 等の共通クラスがあるのに独自にボタン等のスタイルを再実装していないか（ポップアップ以外の独立ページ・新規タブ page でも同様。`base.css` を `<link>` すれば流用できる）
- JS: `Toolkit.*` / `ui-helpers.js` / `utils.js` で提供済みの処理を、モジュール側で再実装していないか
- 同一 PR 内で追加した複数の関数・ファイルの中に、ほぼ同じロジック（同じ API 呼び出し・同じ計算・同じ文字列組み立て等）が複数箇所にあり、片方だけ改善（リトライ処理の追加など）されていて他方に反映されていない、という不整合がないか
- popup / service worker / injected script / 独立ページなど**実行コンテキストが異なる**ためにやむを得ず重複しているコードは、共有不可能な理由を明確にした上で許容してよい。ただしその場合も、同じマジックストリング（ストレージキー名等）を使っているかは目視で突き合わせる
- 上記のような「共有できないので個別実装している」パターンが既存コードに前例がある場合（例: 複数ファイルにまたがる同一のストレージキー文字列）は、既存の慣習と揃っているかを確認する（前例と異なる新しい書き方を持ち込んでいないか）

### 処理の軽量化

- `querySelectorAll` + ループを `querySelector` 1 回で済ませられないか
- 高頻度イベント（input, scroll, resize）にデバウンス / スロットルが必要でないか
- `chrome.storage` への個別アクセスを一括取得にまとめられないか
- ループ内の不変な計算をループ外に出せないか
- 文字列の `+=` 連結を `Array` + `join` に置き換えられないか
- 不要な DOM 再描画（innerHTML の全書き換えなど）を部分更新にできないか

## 出力

指摘事項を以下の形式で報告する:

```
### パフォーマンスレビュー結果

**コード量削減**
- [ ] `ファイル名:行番号` — 指摘内容（改善案）

**共通処理の再利用・切り出し**
- [ ] `ファイル名:行番号` — 指摘内容（改善案）

**処理軽量化**
- [ ] `ファイル名:行番号` — 指摘内容（改善案）

該当カテゴリに指摘がなければそのカテゴリごと省略する。
全て指摘なしの場合: 「パフォーマンス上の問題は見つかりませんでした」
```

修正が求められている場合（issue-handler 経由）は、報告後に指摘箇所を修正する。
